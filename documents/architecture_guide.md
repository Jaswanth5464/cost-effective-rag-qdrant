# High-Performance Cost-Effective RAG Architecture

## Chapter 1: Executive Overview & Motivation
Enterprise Retrieval-Augmented Generation (RAG) systems traditionally rely on managed cloud vector databases like Pinecone or Weaviate Cloud. While managed services simplify initial setup, billing scales directly with total stored vectors and always-on memory pods. For enterprises storing millions of vectors under light or moderate query traffic, paying fixed pod charges creates unnecessary cost overhead.

This architecture demonstrates a production-grade, self-hosted alternative utilizing containerized **Qdrant**, local zero-cost **BAAI/bge-small-en-v1.5** embeddings, and **Gemini 2.5 Flash** for grounded LLM answer generation.

## Chapter 2: Vector Storage & Qdrant Tuning
Qdrant is configured in Docker Compose using HNSW (Hierarchical Navigable Small World) graph indexing combined with Scalar Quantization (SQ8) for minimal memory footprint.

### Core Vector Specifications
- **Embedding Model**: `BAAI/bge-small-en-v1.5`
- **Dense Dimension Size**: 384 dimensions
- **Distance Metric**: Cosine Similarity (`Distance.COSINE`)
- **Index Configuration**: `m=16`, `ef_construct=100`
- **Payload Indexing**: Pre-built keyword indices on high-cardinality fields (`category`, `source`, `document_name`).

## Chapter 3: Idempotent Ingestion Pipeline
To eliminate duplicate vector storage and prevent redundant embedding compute, every document chunk passes through a deterministic hashing engine.

### Hashing Workflow
1. The document is parsed and split into text chunks using LangChain's `RecursiveCharacterTextSplitter` (`CHUNK_SIZE=512`, `CHUNK_OVERLAP=50`).
2. A SHA-256 hash string is generated by concatenating `source_path + page_number + chunk_text`.
3. The SHA-256 string is mapped to a deterministic UUID v5.
4. Before embedding, Qdrant is queried using `get_existing_point_ids()`. Existing Point IDs are filtered out, ensuring **zero duplicate vectors**.

## Chapter 4: Grounded LLM Prompting & Safety
The LLM integration uses Google's `google-genai` SDK with the `gemini-2.5-flash` model. 

### System Instructions
- **Strict Context Boundary**: The model is explicitly instructed to rely ONLY on the provided context blocks.
- **Hallucination Prevention**: If retrieved context is insufficient to answer the question, the LLM is mandated to reply: `"I don't know based on the provided documents."`
- **Source Citation Enforcement**: Every factual sentence must be succeeded by explicit brackets citing document name, page number, and chunk ID.

## Chapter 5: Latency Targets & Performance SLOs
- **Query Embedding Latency**: < 15ms (CPU inference with ONNX runtime / SentenceTransformers)
- **Vector Search Latency (p95)**: < 10ms (Qdrant payload filtering and HNSW retrieval)
- **Gemini 2.5 Flash Generation Latency (p95)**: < 800ms
- **Total System End-to-End Latency Target (p95)**: < 1000ms

## Chapter 6: Evaluation Methodology
Evaluation is conducted across three distinct layers:
1. **Retrieval Accuracy**: Recall@k, Hit Rate@k, Mean Reciprocal Rank (MRR), nDCG@k, and Context Precision.
2. **Answer Quality**: Groundedness/Faithfulness, Answer Relevance, Exact Match (EM), and Token F1.
3. **Latency Benchmarking**: Percentile analysis (p50, p95, mean) computed across 100 queries.
